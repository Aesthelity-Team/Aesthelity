## Verified current behavior

The iOS analysis screen shows fixed DATA-01 scenarios. `DemoAnalysis` reads `expectedFindings`. It does not evaluate a user's routine. `evaluate` builds those findings with three demo rules:

- A product whose `ingredient_list_status` is not `complete` becomes one `unknown` finding.
- A listed ingredient string that casefolds to `DemoProfile.recordedAllergens` becomes one `allergen` finding.
- A product with `subtype` `retinol`, together with a product whose `subtype` is `exfoliant` or `exfoliating`, becomes one `caution` finding. The finding's `ingredient` is null. Its explanation says to try the products on different nights. That sentence is demo copy in `scenarios.json`. It is not a layering rule in this draft.

`DemoFindingKind` is `caution`, `allergen`, or `unknown`. `DemoScenarioType` adds `normal` for a scenario whose demo evaluation returns no findings. Findings have no severity, no rule ID, and no catalog version. `docs/DATA_DICTIONARY.md` says a product is never given a universal safety rating, and that normal means no findings under the limited demo rules.

`IngredientAnalysisInput` is one product: `productID`, `listStatus`, `confirmedIDs`, and `uncertaintyPreserved`. It is not `Codable`. It does not carry period, routine order, original rows, `suggestedID`, `candidateIDs`, `catalogVersion`, or classes. `uncertaintyPreserved` is one boolean for every gap. `confirmedIngredientIDs(using:)` can still list member IDs when `catalogVersion` is missing or different. `isFullyResolved(using:)` is then false. PD-03 tells a caller to refresh with `normalizeStoredProduct` before treating that mapping as current.

`RoutineStepItem` stores a title and a step number, not a catalog product ID. `RoutinePeriod` raw values are `AM` and `PM`. `DemoRoutineTime` raw values are `am` and `pm`. `SkinProfile` stores `avoidedIngredients` and says avoidance is a preference, not a diagnosed allergy. It has no recorded-allergy field. `ConfidenceScoreView` shows a static demo score. This draft defines no percentage and no confidence score.

## Matching

Proposed contract behavior:

- A rule may match a confirmed canonical ingredient ID, or a catalog class the rule names.
- A class describes catalog membership. It does not establish equivalent effects and does not justify a rule by itself. `glycolic-acid` has classes `aha` and `exfoliant`. A rule that names `exfoliant` does not also match on `aha`.
- `suggestedID`, `candidateIDs`, and `DemoProduct.subtype` are not confirmed ingredient match keys. `DemoProduct.category` is the product type, such as `serum`. It is not an interaction category and not a match key.
- Confirmed identity requires `mapping` `confirmed`, an `ingredientID` present in the active catalog, a `catalogVersion` equal to `activeCatalogVersion`, and a list status that agrees with the row count. A partial list may still contain confirmed identities for the rows that are present.
- Class lookup uses `CanonicalIngredient.classes` from the catalog whose `version` equals `activeCatalogVersion`, through `IngredientNormalizer.ingredient(withID:)`. Classes are not copied onto the stored product.
- Several rows with the same canonical ID are one identity for matching. The finding lists that ID once. The source rows stay in `ingredients`. Product lists are not deduplicated.
- A finding that involves more than one product lists each affected `productID` once, in routine order, under one `ruleID`.
- Analysis does not call `normalizeStoredProduct` and does not rewrite ingredient text, list status, or `catalogVersion`.

`analysisInput(using:)` does not apply the version check above. It can return member IDs while `uncertaintyPreserved` is true. This draft asks AN-03 not to treat those IDs as confirmed matches. That follows PD-03's instruction to refresh before treating a stale mapping as current. It is stricter than matching every ID in `confirmedIDs`. Mia and Belle need to confirm it.

```json
{"originalText": "Retinol", "mapping": "confirmed", "ingredientID": "retinol"}
```

```json
{"originalText": "Retinol", "mapping": "confirmed", "ingredientID": "retinol"}
```

Those two rows are one confirmed `retinol`. Neither row is deleted.

### Where a ticket requirement meets an invariant

The demo allergen rule matches label text, not a confirmed ID. The invariant says production matching uses confirmed IDs and named classes only. This draft keeps the invariant and leaves the demo matcher in `evaluate`. A production allergen rule would have to use confirmed IDs. If the team wants production matching to keep the demo's string comparison, that is a conflict to resolve in review. This draft does not relax the invariant.

Issue #23 asks the engine to account for order and layering. The matching invariant does not use position as an ingredient identity. This draft preserves order for display and finding order, and does not evaluate it. A later layering rule that needs position would not by itself become an ingredient match key, but the team has to agree before any rule treats position as a condition. Until then, reversing two products does not change whether an ingredient rule matches.

## Interaction categories

Unresolved as an approved taxonomy. Proposed for review.

Issue #22 scenario 1 says two or more normalized ingredients produce the appropriate compatibility or interaction category. The ticket does not name the categories. This section proposes a short taxonomy. It is not approved.

Four ideas stay separate:

| Idea | Field | What it answers |
|---|---|---|
| Interaction category | `categoryID` | What subject the finding is about |
| Outcome | finding `outcome`, or routine `outcome` | What the evaluation concluded |
| Severity | `severity` | How strongly an approved rule says to emphasize the finding |
| Coverage | `completeness` | Whether the routine was fully checked |

`categoryID` is not `DemoProduct.category`.

| `categoryID` | Status | Meaning | Outcome it can carry |
|---|---|---|---|
| `ingredient-combination` | Proposed for review | An approved rule matched two or more confirmed identities | `caution`. `conflict` only after that outcome is accepted |
| `recorded-allergy` | Proposed, not executable | A confirmed ingredient matched a recorded allergy | `allergen`, after the allergy input and matcher exist |
| `coverage-gap` | Proposed for review | A needed fact was missing or uncertain | `unknown` |

A combination finding and a coverage finding can both be present. Coverage does not cancel the combination, and the combination does not make coverage complete.

`recorded-allergy` has no fixture with expected findings, because the input does not exist. Layering is not a category in this taxonomy. It is a separate open topic below. If the team wants a `layering-order` category before any layering rule exists, that is a decision. This draft does not add one.

There is no category for "safe" or "normal." An empty result is the normal / no-findings outcome, not a category.

## Normal and no findings

Proposed for review. Runtime enums stay as they are.

Issue #22 uses the outcome word `normal`. `DemoScenarioType.normal` means the demo evaluator returned no findings. `DemoAnalysisState.normal` is the demo screen state for that scenario. This draft does not rename either enum.

Proposed mapping:

| Ticket word | Machine result | User-facing words | When it is allowed |
|---|---|---|---|
| `normal` | `outcome` `noFindings` and `completeness` `complete` | "No matching rules" | Every product was checked under the rules this contract is allowed to run, and none matched |

`noFindings` is not a finding. It is the routine outcome when `findings` is empty and coverage is complete. The proposed display string is "No matching rules." It is not "Normal," "Compatible," or "Safe."

An empty finding list with `completeness` `incomplete` is not `noFindings` and not the ticket's normal outcome. Unknown findings must be present so the gap stays visible. `no-matching-rules.json` is the complete case. The unknown fixtures are the incomplete case.

AN-03 can implement this shape after Mia accepts the tokens. It must not treat an empty list as safe. It must not rename `DemoScenarioType` or `DemoAnalysisState`. The team still needs to accept `noFindings` as the machine token. If the team prefers the JSON value `normal`, the display string still must not imply safety. That choice is open.

## Caution

Proposed for review.

A caution is an approved rule that matched confirmed input. The finding's category is the subject of that rule. For the example below, the category is `ingredient-combination`. Caution does not mean the products are unsafe, and it does not tell the user to reorder them.

The retinoid and exfoliant example is example-only. It is not an approved caution. Its fixtures show the result shape. They are not engine expectations until the team approves the rule, the category, and any severity assignment.

AN-03 should not ship that rule as a default. Demo `caution_pm` stays a demo subtype rule.

## Unknown and missing data

Proposed for review.

Issue #22 scenario 2 says missing or uncertain information is marked unknown or requiring caution, and is not automatically safe. This draft uses `unknown` for every gap and reserves `caution` for an approved rule match. The ticket allows either mark. Using unknown for all gaps is a recommendation, not a silent deletion of the caution option. The team can decide that a particular gap is caution instead. No such gap is defined here.

Unknown findings use category `coverage-gap`. They do not carry confirmed ingredient IDs.

| `ruleID` | When it fires |
|---|---|
| `coverage.partial-list` | `listStatus` is `partial` and the row count agrees |
| `coverage.unavailable-list` | `listStatus` is `unavailable` and the row array is empty |
| `coverage.contradictory-list-status` | Status and row count disagree. `listStatusAgreesWithRowCount` is false |
| `coverage.stale-catalog` | `catalogVersion` is an integer other than `activeCatalogVersion` |
| `coverage.missing-catalog-version` | `catalogVersion` is null or omitted |
| `coverage.unresolved-row` | The row is `ambiguous`, `uncertain`, or `unmatched`, or its confirmed `ingredientID` is absent from the active catalog |

`reasonCode` on `coverage.unresolved-row` is `ambiguous`, `uncertain`, `unmatched`, or `absent-catalog-id`. A member ID on a stale or missing version is the version finding, not an unresolved row. If a stale product also has an ambiguous row, emit both. Do not drop a coverage finding because a caution also matched.

`Vitamin C` is the catalog's ambiguous term for `ascorbic-acid`, `ascorbyl-glucoside`, `magnesium-ascorbyl-phosphate`, and `sodium-ascorbyl-phosphate`. Those candidates are not confirmed ascorbic acid. `Niacinimide` is an uncertain spelling whose tested `suggestedID` is `niacinamide`. The suggestion is not confirmed niacinamide.

| Situation | Confirmed for matching | Findings | Completeness | Routine outcome |
|---|---|---|---|---|
| Complete, version matches, every confirmed ID is a member, no rule matches | Yes | None | `complete` | `noFindings` |
| Complete, version matches, an approved rule matches | Yes, for those identities | Caution, or another accepted outcome | `complete` | `findings` |
| Partial list, version matches, a present row supplies a confirmed match | Yes, for present member IDs only | The match and `coverage.partial-list` | `incomplete` | `findings` |
| Partial list, version matches, no rule matches | Present member IDs only | `coverage.partial-list` | `incomplete` | `findings` |
| Unavailable list, empty | No | `coverage.unavailable-list` | `incomplete` | `findings` |
| Ambiguous row, including `Vitamin C` | No for that row | `coverage.unresolved-row`, `ambiguous` | `incomplete` | `findings` |
| Uncertain spelling, including a `suggestedID` | No for that row | `coverage.unresolved-row`, `uncertain` | `incomplete` | `findings` |
| Unmatched text | No for that row | `coverage.unresolved-row`, `unmatched` | `incomplete` | `findings` |
| Stored ID absent from the active catalog, including `nonexistent-id` | No for that row | `coverage.unresolved-row`, `absent-catalog-id` | `incomplete` | `findings` |
| `catalogVersion` differs from the active catalog | No, including IDs that are still members | `coverage.stale-catalog` | `incomplete` | `findings` |
| `catalogVersion` null or omitted | No | `coverage.missing-catalog-version` | `incomplete` | `findings` |
| Status contradicts the row count | No | `coverage.contradictory-list-status` | `incomplete` | `findings` |
| No ingredient list was supplied to normalization | Not an input | PD-03 does not invent an empty complete product | None | Do not return `noFindings` |
| Routine `products` empty, or a product ID repeated | Invalid input | None | None | Do not return `noFindings` |

`mask_partial` is the stored partial demo product. Its rows are Water and Glycerin, so it cannot show the example rule. The partial fixture uses a stated subset of `serum_retinol` and does not edit `products.json`.

A contradictory list still exposes stored rows in PD-03. This draft does not match identities from a contradictory list. A stale member ID can still appear in `confirmedIDs` today. This draft still refuses the match until the versions are equal. Both points need Mia and Belle.

AN-03 can implement the coverage rows in that table without an approved clinical rule. It must not report them as caution, and it must not omit them to make a matched routine look fully checked.

## Allergen

Unresolved decision. No production allergy model is created here.

Issue #22 requires an allergen outcome and a fixture. Issue #23 requires the engine to identify that outcome. The ticket does not define the allergy input.

Verified current behavior:

- `DemoProfile.recordedAllergens` is a list of strings on demo profiles. `profile_limonene_allergy` records the string `Limonene`.
- `evaluate` casefolds that string against listed ingredient text. Scenario `allergen_mist` uses `mist_fragranced`, whose label includes `Limonene`.
- The catalog ID for that name is `limonene`, with classes `fragrance` and `fragrance-allergen`. The demo matcher does not use the ID or the class.
- `SkinProfile.avoidedIngredients` is a preference list of `NormalizedIngredient` values, including unresolved text. The type says this is not a diagnosed allergy. There is no recorded-allergy field on `SkinProfile`.

Proposed contract, not an implemented model:

- Avoidance and a recorded allergy stay different inputs. AN-03 must not read `avoidedIngredients` as allergies.
- A production allergen finding needs a recorded-allergy input the app does not have, a confirmed ingredient ID on that record, and an approved matcher from that ID to confirmed product rows.
- The matcher would follow the same identity rules. A `suggestedID` or `candidateIDs` entry would not match. Class `fragrance-allergen` would not match unless an approved rule names it. This draft does not name it.
- A confirmed allergy match on a partial list could coexist with `coverage.partial-list`. That is the same coexistence rule as any other confirmed match. It is not a reason to invent the allergy input.
- Until that input and matcher exist, AN-03 must not emit `allergen`. `allergen_mist` stays demo-only.

What is still unknown: who records an allergy, how it is stored, and whether a class may ever be an allergy match.

What the team needs to decide: the input, the matcher, and whether issue #22's allergen fixture can wait until that input exists.

Effect on AN-03 and fixtures: do not add profile fields, do not copy `evaluate`'s string match into the engine, and do not add an expected allergen finding. `open-decisions.json` lists what a future fixture needs. A later fixture could use `mist_fragranced` and ID `limonene` only after the allergy input exists. This draft does not give that fixture an expected finding.

## Conflict

Unresolved decision. Proposed distinction, not an approved outcome.

Issue #22 requires a conflict outcome and a fixture. Issue #23 scenario 2 says ingredients that may conflict or require caution produce an interaction and a severity. The codebase has no `conflict` value. `DemoFindingKind` does not include it. No comment defines how conflict differs from caution.

Proposed definition: caution means one approved rule matched confirmed input and asks for review. Conflict means two approved rules match the same products and cannot both be followed. Conflict is an outcome on category `ingredient-combination`, not a separate category and not a medical grade.

That distinction is implementable only after two approved rules exist. It is useful if the product needs to say "these instructions disagree" rather than "please review this match." It is not useful as a second name for a strong caution. If the team wants strength, the severity scale below should carry it, and conflict should not be added.

The example retinol rule cannot demonstrate conflict. It is one example-only rule, and it is not approved. A future fixture needs two approved rules, a routine of existing fictional products where both match, a decision that they cannot both be followed, and a severity assignment if scenario 3 applies. This draft does not invent that second rule or an expected conflict finding. `open-decisions.json` records the gap.

AN-03 must not emit `conflict` from the example rule, from a coverage gap, or from demo subtype pairs.

## Severity

Unresolved decision. The scale is proposed. No level is assigned.

Issue #22 scenario 3 and issue #23 require a caution or conflict result to include a severity and an explanation. No file in this repository defines a scale. `ConfidenceScoreView` is a static demo screen, not this field.

Proposed vocabulary, for interface emphasis only:

| Value | Proposed meaning |
|---|---|
| `low` | Show the finding without extra emphasis |
| `moderate` | Show the finding as something to review |
| `high` | Use the strongest emphasis this scale has |

These words are not medical grades, not probabilities, and not percentages. Defining this list does not assign a level to any skincare rule. Assignment is a separate review for each approved rule. This draft assigns none. `assignedOnRules` in `open-decisions.json` is empty.

On a finding, omit `severity` when no level has been assigned. Do not send null. Null is not a level.

The example rule therefore omits `severity`. Its fixtures are valid illustrations of matching, product relationships, and sample explanation text. They are not valid executable expectations for scenario 3, because the required severity is intentionally absent. AN-03 must not fill in `low`, `moderate`, or `high` for that rule. An explanation without an assigned severity does not satisfy scenario 3.

What the team needs to decide: whether these three words are the scale, and, later, which approved rule gets which word. Those are two decisions. Accepting the scale does not approve a retinoid severity.

## Routine order and layering

Unresolved decision. No order-dependent skincare advice is proposed.

What ordered input enables: the routine array is the product order. Result `productIDs` keep that order. A multi-product finding lists affected products in that order. Finding sort uses that order. `period` records whether the routine is `am` or `pm`. One evaluation is one period. AM products are not included in a PM result.

What ordered input does not do: it does not change whether an ingredient rule matches. It does not recommend a new sequence, a wait between products, or use on different nights.

Issue #26, AN-06, is the Sprint 3 story for layering explanation. It asks for layering order rules, a recommended sequence, a reason for that sequence, and honest handling when the order cannot be determined. It is open, has no comments, and no layering rule is in the repo. Its acceptance criteria are not met by this draft.

Proposed boundary for review:

- AN-03 preserves order and evaluates ingredient rules that do not depend on position.
- AN-06 owns the recommended sequence and the explanation of that sequence, after layering rules exist.
- This draft does not define AN-06's output.

Missing before order can be evaluated: an approved rule that says what about order matters, and the product facts that rule needs. Product type and subtype are present on `DemoProduct` and are not ingredient match keys. This draft does not turn them into layering keys either.

The demo sentence in `caution_pm` about different nights stays demo copy. Copying it into a production finding would invent layering advice. The example fixtures do not copy it.

AN-03 should keep array order and should not return a recommended sequence. The team needs to accept or redraw the AN-06 boundary before any order-dependent rule is implemented.

## Input and output

Proposed for review. Mia owns whether AN-03 can implement this interface. `IngredientAnalysisInput` stays the single-product derivation. The proposed routine input does not replace it and does not change `analysisInput(using:)`.

Routine input:

| Field | Required | Allowed values | Meaning |
|---|---|---|---|
| `period` | Yes | `am`, `pm` | Same tokens as `DemoRoutineTime`. `RoutinePeriod` uses `AM` and `PM`. This contract does not map them. |
| `activeCatalogVersion` | Yes | Integer | Catalog used for membership and classes. The bundled file's `version` is 3. |
| `products` | Yes | Non-empty array | Routine order. Array order is the only order. |

Product object, aligned with `NormalizedProductIngredients`:

| Field | Required | Allowed values | Meaning |
|---|---|---|---|
| `productID` | Yes | Non-empty string | Stable identity. Unique inside one routine. |
| `listStatus` | Yes | `complete`, `partial`, `unavailable` | `IngredientListStatus`. Not derived from how many rows matched. |
| `catalogVersion` | Yes | Integer or `null` | An omitted key and JSON `null` both mean missing. A present integer is not rewritten. |
| `ingredients` | Yes | Array, possibly empty | Label order. `originalText` stays on each row. |

Row object, aligned with `NormalizedIngredient` JSON:

| Field | Required | Allowed values | Omitted versus null |
|---|---|---|---|
| `originalText` | Yes | String, preserved exactly | Required. Do not replace it with `CanonicalIngredient.name`. |
| `mapping` | Yes | `confirmed`, `uncertain`, `ambiguous`, `unmatched` | Required. |
| `ingredientID` | Only when `confirmed` | Canonical slug | Omit otherwise. Do not send null. |
| `suggestedID` | Only when `uncertain` | Canonical slug | Omit otherwise. Not a match key. |
| `candidateIDs` | Only when `ambiguous` | Two or more distinct slugs | Omit otherwise. Not match keys. |
| `warning` | No | PD-03 warning object | Fixtures omit it. Not a match key. Do not send null. |

Not part of the input: product subtype, product type, avoided ingredients, demo `recorded_allergens`, concentrations, frequency, and reminders. A recorded allergy is also absent until the allergen decision adds one. This draft does not add that field.

Invalid input must not come back as `noFindings` or as complete coverage. This draft does not choose the error type. Empty `products`, a repeated `productID`, a missing `period` or `activeCatalogVersion`, and a row that breaks the PD-03 mapping shape are invalid. Whether one product may occupy two steps is open. Demo scenarios require unique product IDs, so this proposal does too.

Routine result:

| Field | Required | Allowed values | Meaning |
|---|---|---|---|
| `period` | Yes | `am`, `pm` | Echo of the input. |
| `activeCatalogVersion` | Yes | Integer | Echo of the catalog used. |
| `outcome` | Yes | `noFindings`, `findings` | `noFindings` only when `findings` is empty and `completeness` is `complete`. This is the proposed machine form of the ticket's `normal`. |
| `completeness` | Yes | `complete`, `incomplete` | Independent of caution. |
| `productIDs` | Yes | Input IDs in routine order | Includes products with no finding. |
| `findings` | Yes | Array | Empty only for `noFindings`. |
| `limitations` | Yes | Non-empty array of strings | Sample copy in the fixtures. Includes that `noFindings` is not a safety assessment. |

Finding:

| Field | Required | Allowed values | Omitted versus null |
|---|---|---|---|
| `ruleID` | Yes | Stable ID | Required. |
| `ruleStatus` | Yes | `example-only`, `proposed` | Coverage IDs stay `proposed` until this contract is accepted. |
| `outcome` | Yes | `caution`, `unknown`, `allergen`, `conflict` | Fixtures emit only `caution` and `unknown`. The other two are defined above and are not emitted yet. |
| `categoryID` | Yes | `ingredient-combination`, `recorded-allergy`, `coverage-gap` | Stable subject. `recorded-allergy` has no expected finding in this draft. |
| `categoryLabel` | Yes | Short string | Presentation only. Fixture text is sample copy. |
| `productIDs` | Yes | Non-empty subset, routine order | Each ID once. |
| `ingredientIDs` | Yes | Distinct canonical IDs | IDs that satisfied a caution rule, first seen in routine order. Empty array for unknown. Do not send null. |
| `matchedClassIDs` | No | Class slugs the rule named and the match used | Omit when no class matched. Do not send an empty array or null. |
| `severity` | No | `low`, `moderate`, `high` | Omit until an approved rule assigns one. Do not send null. No fixture includes it. |
| `originalText` | No | Label text | Required with `rowIndex` for a row-level unknown finding. |
| `rowIndex` | No | Zero-based integer | Omit together with `originalText`. |
| `reasonCode` | No | The four unresolved-row codes | Required for `coverage.unresolved-row`. Omit otherwise. |
| `explanation` | Yes | String | Sample copy in fixtures. |
| `reason` | Yes | String | Sample copy in fixtures. |
| `limitations` | Yes | Non-empty array of strings | Sample copy in fixtures. |

Finding order: earliest affected product, then `caution` before `unknown`, then a row-level finding before a product-level finding, then `rowIndex`, then `ruleID`. `allergen` and `conflict` are not in this sort until they are emitted. If they are accepted later, they sort with `caution`, before `unknown`.

Display names are not identity fields.

- Product title: `DemoProduct.name`. `serum_retinol` is `Retinol Night Serum (Fictional)`.
- Confirmed ingredient title: `CanonicalIngredient.name`. `glycolic-acid` is `Glycolic Acid`.
- Unresolved line: `originalText`.

`categoryLabel` is the only presentation name stored on the finding.

## Example rule

Example-only. Not approved, not clinically validated, and not a reproduction of the demo subtype rule. In catalog version 3, class `exfoliant` is on `glycolic-acid`, `lactic-acid`, `mandelic-acid`, and `salicylic-acid`. Naming that class does not mean those ingredients have the same effect. `retinal` and `retinyl-palmitate` are class `retinoid` and do not satisfy this rule. Whether a future rule should name class `retinoid` instead of ID `retinol` is open. `severity` is omitted on purpose.

`serum_retinol` plus `treatment_exfoliant` satisfies both this example and the demo subtype rule. The rules are not the same. `treatment_spot` contains salicylic acid, whose classes include `exfoliant`, and its subtype is `spot`, so the demo rule does not select it. This example would, if it were approved. A subtype of `retinol` without confirmed ID `retinol` would satisfy the demo rule and would not satisfy this example.

```json
{
  "ruleID": "example.retinol-with-exfoliant-class",
  "ruleStatus": "example-only",
  "outcome": "caution",
  "categoryID": "ingredient-combination",
  "match": {
    "allOf": [
      {"ingredientID": "retinol"},
      {"classID": "exfoliant"}
    ]
  }
}
```

Both criteria are required. They may come from one product or from two. Order does not matter. Subtype does not matter.
