# PD-02: Manual product input

## Checkpoint 2: Draft validation and submission

`ManualProductDraft.submit(using:)` returns either a prepared `ManualProduct` or field-specific errors. It does not save, navigate, or run analysis. The draft retains entered text, and the product retains the original ingredient label.

Rules:

- Product name and at least one ingredient are required. Brand and category are optional. No name or brand length limit is imposed.
- Prepared metadata is trimmed and Unicode format characters are removed. Empty brand becomes `nil`.
- Ingredient parsing reuses the existing heading, separator, percentage, bracket, and numeric-comma handling. Empty separators are ignored.
- Each prepared ingredient must contain a letter and have at most 120 characters. Entries that cleanup would discard, including standalone footnote text, require correction rather than being silently omitted in manual submission.
- Brackets must balance. Real control characters are rejected; line breaks are permitted as ingredient-list separators. Invisible Unicode format characters are removed from prepared ingredient names.
- Normalization preserves ingredient order and duplicates. Unknown, ambiguous, and uncertain results retain warnings; a normalization match does not establish safety.
- Entry errors carry the original segment text and a zero-based index among nonempty parsed entries. Whole-field errors have no entry index.

The existing `ingredientNames(in:)` API is unchanged. The added `entriesForValidation(in:)` API exposes nonempty entries even when cleanup produces no name.

## Checkpoint 3: Local product persistence

Manual products are saved locally on the phone, as agreed for PD-02. `ManualProductStore` follows the existing `SkinProfileStore` architecture: a main-actor observable object, injected once by `AesthelityApp`, backed by an atomic JSON archive in Application Support (`ManualProducts/products.json`) with complete file protection.

The store accepts a validated `ManualProduct`. Saving inserts by stable UUID or updates the existing position for that UUID. Matching names do not merge distinct products. Raw labels, normalization metadata, order, duplicates, optional metadata, and manual provenance survive reload. Saving does not normalize again, invoke analysis, or claim safety.

The archive and each product have schema version 1. Corrupt, unsupported, or duplicate-ID archives remain untouched and expose a load error. Saving is blocked after a load error so an empty in-memory list cannot overwrite existing records. Recovery/export UI remains future work. Failed writes throw without publishing an unsaved change. No delete/reset API is introduced in this checkpoint.

The future form should submit its draft, save the returned product using the shared store, then continue only after save succeeds. Keep the returned product ID when retrying a save rather than submitting again and generating another UUID. The form and save-error display are a later checkpoint.

## Selected handoff adapter

`ManualProductAnalysisInput` encodes `productID`, `listStatus`, optional `catalogVersion`, and ordered ingredient rows. Rows use the draft AN-03 `mapping` vocabulary: `confirmed`, `uncertain`, `ambiguous`, and `unmatched`. Suggestions and candidate IDs remain separate from confirmed IDs, and warnings retain their text. The adapter neither saves nor evaluates ingredients.

Both `listStatus` and `catalogVersion` are explicit initializer arguments. The product model does not currently record label completeness or the catalog version used for normalization. The future form/coordinator must obtain completeness explicitly; when normalization provenance is unavailable (including existing stored products), pass `nil` for catalog version so Python can require refresh. Do not substitute the currently bundled catalog version for an unknown historical version. Collecting/storing these metadata fields and supporting refresh requires a later agreed model change.

Future coordinator sequence:

1. Submit the draft and retain the returned product for retries.
2. Call `try manualProductStore.save(product)` and present errors on failure.
3. Build `ManualProductAnalysisInput(product: product, listStatus: explicitlyChosenStatus, catalogVersion: knownNormalizationVersionOrNil)`.
4. TODO(PD-02/AN-03): Send the payload through the team's agreed authenticated API once it exists. Do not navigate to a fixed demo finding or claim analysis success while this endpoint is absent.

The adapter targets the unmerged AN-03 draft at `2ec1355`; review compatibility again when that branch is merged. The storage archive remains independent of this transport contract.

After the selected adapter, the app built and all 140 unit tests passed (three additional adapter tests). These check encoded field names, all mapping states, warnings, duplicates, explicit list statuses, and missing catalog version. They do not verify a deployed API or run the unmerged Python engine.

## Checkpoint 4: Manual entry form

Open Library → Your manual products → Add product. The form starts empty, with optional brand/category, a multiline ingredient label, and inline validation using `ManualProductDraft`. Review ingredients prepares an ordered result and shows unresolved warnings/suggestions without replacing entered text. Editing any field invalidates the prior review. Save product on this device writes the reviewed record and dismisses only after success; failures retain the draft and the same product UUID for retry. Cancel and sheet dismissal do not save.

The Library lists saved manual products separately from demo catalog records, with a “Manually entered · Not analyzed” label. Tapping one opens its metadata, original label, and ingredient review. No demo finding, safety badge, analysis request, or cloud upload is attached to a manual entry.

This form completes local entry and saving. Analysis handoff remains a placeholder: the form does not infer whole-label completeness or a normalization catalog version from valid syntax. The next analysis-integration checkpoint must collect/store those metadata explicitly and agree on an endpoint before using the selected adapter.

`ManualProductUITests` is added to the existing registered UI-test file. Its launch flags isolate product storage and startup preferences from ordinary app use: `--pd02-ui-testing`, `--pd02-reset-products`, and a test-only `--pd02-save-failure` path. Tests exercise save/relaunch, normalization warnings, required/invalid input and correction, cancellation, and save failure/retry.
