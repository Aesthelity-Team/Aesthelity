# PD-03: Ingredient alias mapping

Proposed contract for team review. Issue #19 and PR #83 do not record an agreement from Belle (catalog import and Firestore) or Mia (analysis engine). This document describes the behavior implemented in this repository and the handoff those integrations can code against.

Normalization is not a safety assessment. A confirmed ID means the printed name matched one canonical ingredient. It does not mean the ingredient or the product is safe.

## What this change covers

`IngredientNormalizer` maps one ingredient string, or an ordered list of strings, onto the bundled catalog in `Aesthelity/Aesthelity/Resources/SampleData/ingredient-aliases.json`.

`normalizeStoredProduct(id:ingredientTexts:listStatus:)` applies that mapping to a product whose ingredients are still stored as strings. `normalizeCatalogProduct(_:)` does that for a current `DemoProduct`. Neither method writes Firestore, changes `Resources/DemoData`, or runs analysis rules.

Manual product entry is the same function: pass the product ID the caller already has, the ingredient strings in label order, and the list status the caller already knows. This PR does not add the catalog browser or the manual-entry screen.

Skin-profile avoidance is a separate path. `SkinProfileDraft.submit` normalizes entered preferences and deduplicates them. Product lists do not deduplicate. Two label lines that share a canonical ID stay two rows.

## Canonical IDs

Approved ingredient IDs are stable slugs: lowercase letters and digits, with words joined by single hyphens (`water`, `niacinamide`, `ascorbic-acid`). Display names and aliases are not IDs. The same ID is used for every approved spelling of that ingredient.

`CanonicalIngredientID.isValid` is the one syntax check. Catalog loading and stored-record decoding both use it. These values are rejected, not trimmed or rewritten:

`""`, `"   "`, `" water "`, `"Niacinamide"`, `"ascorbic acid"`, `"-water"`, `"water-"`, `"water--test"`.

`IngredientAliasCatalog.load` rejects a catalog with a duplicate ID, a non-slug ID or class, an empty name, or one exact name claimed by two ingredients. Ambiguous terms must name at least two known IDs and must not reuse an approved exact alias. A reference with a review status other than `reviewed` cannot supply an approved exact alias.

Class slugs such as `vitamin-b3` group ingredients for later rules. A class is not an alias and does not by itself match label text.

Syntax is not catalog membership. A decoder can accept `nonexistent-id` because it is a valid slug. Membership is checked only when a stored product is turned into analysis input, against the `IngredientNormalizer` the caller supplies. Decoding does not load the app bundle.

## Mapping states

| State | `mapping` | Confirmed `ingredientID` | Other IDs | `needsReview` |
|---|---|---|---|---|
| Confirmed | `confirmed` | The canonical ID | None | No |
| Uncertain | `uncertain` | Absent | `suggestedID` only | Yes |
| Ambiguous | `ambiguous` | Absent | At least two distinct `candidateIDs` | Yes |
| Unmatched | `unmatched` | Absent | None | Yes |

`NormalizedIngredient.ingredientID` returns a value only for `confirmed`. A suggestion or a candidate list is not a confirmed ID. The explicit `mapping` object and the legacy `status` object both go through `validatedStatus`, so a legacy row cannot skip these rules:

- `confirmed` has one valid `ingredientID` and no suggested or candidate IDs.
- `uncertain` has one valid `suggestedID` and no confirmed or candidate IDs.
- `ambiguous` has at least two distinct valid candidate IDs and no confirmed or suggested ID. A repeated ID does not count as a second candidate and is rejected.
- `unmatched` has none of those IDs.

A payload that contains both `mapping` and `status` is rejected. One representation cannot silently override the other. Valid historical rows that contain only `status`, and whose IDs already follow these rules, still decode. New writes emit `mapping` and do not emit `status`. `SkinProfile.schemaVersion` stays 1. A saved profile whose ingredient ID fails these rules does not decode; the profile file is not deleted, and the existing store load error is shown. The normalizer does not write those malformed IDs.

Uncertain results are close spelling matches. Ambiguous results are names the catalog already treats as families or collisions, such as `Vitamin C`, or exact names that the reference data assigns to more than one ingredient. Unmatched results have no exact or acceptable close match. All three keep a warning. None of them is a known ingredient for analysis.

The original string is stored on `originalText` unchanged, including case and surrounding spaces. List order is the array order of those rows.

## JSON shape

New files use the explicit fields below. A saved profile that has only the legacy `status` object still decodes, as described above.

Confirmed:

```json
{"originalText":"Nicotinamide","mapping":"confirmed","ingredientID":"niacinamide"}
```

Uncertain:

```json
{"originalText":"Niacinimide","mapping":"uncertain","suggestedID":"niacinamide","warning":{"input":"Niacinimide","message":"..."}}
```

Ambiguous:

```json
{"originalText":"Vitamin C","mapping":"ambiguous","candidateIDs":["ascorbic-acid","ascorbyl-glucoside","magnesium-ascorbyl-phosphate","sodium-ascorbyl-phosphate"],"warning":{"input":"Vitamin C","message":"..."}}
```

Unmatched:

```json
{"originalText":"Unobtainium Extract","mapping":"unmatched","warning":{"input":"Unobtainium Extract","message":"..."}}
```

A product record stores the caller's product ID, the list status, the ordered rows, and the catalog version used to normalize them. This is `pd03-example-serum` from the bundled fixture, with warnings left out of the excerpt. `catalogVersion` is the `version` in `ingredient-aliases.json` (3 when this contract was written). Tests compare an encoded record with the loaded catalog's `version`. Adding the field does not change that content version.

```json
{
  "productID": "pd03-example-serum",
  "listStatus": "complete",
  "catalogVersion": 3,
  "ingredients": [
    {"originalText": "Nicotinamide", "mapping": "confirmed", "ingredientID": "niacinamide"},
    {
      "originalText": "Vitamin C",
      "mapping": "ambiguous",
      "candidateIDs": [
        "ascorbic-acid",
        "ascorbyl-glucoside",
        "magnesium-ascorbyl-phosphate",
        "sodium-ascorbyl-phosphate"
      ]
    },
    {"originalText": "Unobtainium Extract", "mapping": "unmatched"}
  ]
}
```

`listStatus` is `complete`, `partial`, or `unavailable`. Those raw values match the demo catalog. Profile JSON and this product record use camelCase. `Resources/DemoData` remains snake_case and is decoded into `DemoProduct` before mapping.

Stored fields are `productID`, `listStatus`, `catalogVersion`, and `ingredients`. `confirmedIngredientIDs(using:)`, `isFullyResolved(using:)`, and `analysisInput(using:)` are derived. They are not stored, and a stored Boolean cannot turn uncertainty off. `IngredientAnalysisInput` is not `Codable`.

`catalogVersion` is the alias catalog's content version. It is not `SkinProfile.schemaVersion`, and it is not the example fixture's `schemaVersion`. A record written before this field existed decodes with `catalogVersion == nil`. Nil is not rewritten to the active version when the record is read or encoded again. An equal version does not by itself prove that an ID is in the catalog.

`confirmedIngredientIDs(using:)` keeps a stored confirmed ID only when `ingredient(withID:)` finds it in the normalizer's catalog. An unknown slug such as `nonexistent-id` is omitted. The method does not replace it with a match of `originalText`. `isFullyResolved(using:)` is false unless `catalogVersion` equals that normalizer's version, the list is complete and consistent, and every row's confirmed ID is a member. `analysisInput(using:)` sets `uncertaintyPreserved` from that result. A missing or different catalog version therefore stays unresolved even when the stored IDs are still members. Those member IDs can still appear in `confirmedIDs`, and `uncertaintyPreserved` stays true.

Refreshing a missing or different version is explicit. Call `normalizeStoredProduct` with the stored product ID, the row `originalText` values in order, and the stored list status. The new record uses the active catalog version and the current text mappings. It does not copy an unknown stored ID into a new identity. `analysisInput(using:)` does not rewrite the stored record.

## List completeness

List status is separate from each row's mapping.

These outcomes assume the record's `catalogVersion` matches the normalizer. A missing or different version keeps `uncertaintyPreserved` true even when the rows below would otherwise be fully resolved.

| Situation | Rows | `uncertaintyPreserved` |
|---|---|---|
| Complete list, every confirmed ID is in the active catalog | The full label, in order | No |
| Complete list with any uncertain, ambiguous, unmatched, or unknown confirmed ID | Every stored string, including unresolved ones | Yes |
| Partial list | Only the known portion, in stored order | Yes, even when every present row is a catalog member |
| Unavailable list | Empty when the stored data agrees with the status | Yes |
| Complete list with no rows | Empty. The status does not agree with the row count | Yes |
| No list was supplied | The adapter is not called and does not invent an empty complete product | Yes |

An unavailable list that still contains strings keeps those rows and their individual mapping, and `listStatusAgreesWithRowCount` is false. The product is not fully resolved. DATA-01 already rejects that shape in the demo files. Belle's importer should keep rejecting it before storage. This adapter does not drop the rows or mark them safe.

A partial or unavailable list can still expose confirmed IDs for the rows that are present. Those IDs do not make the missing portion known.

## Example

`Aesthelity/Aesthelity/Resources/SampleData/pd03-product-example.json` is a fictional product, `pd03-example-serum`. Its label order is Nicotinamide, Vitamin C, Unobtainium Extract. `PD03ProductExample.load` reads that file, and `IngredientNormalizerTests.productExampleMatchesTheNormalizerAndRoundTrips` runs the normalizer and checks the expected states: confirmed `niacinamide`, ambiguous vitamin C candidates, and unmatched text. The product ID and order stay as stored. The list is complete, and the product is still not fully resolved, because two rows have no confirmed ID.

## Vitamin B3

`Vitamin B3` is not an approved alias of `niacinamide`. The name covers more than one compound, including nicotinamide and nicotinic acid. The catalog maps the exact alias `Nicotinamide` to `niacinamide` and uses `vitamin-b3` only as that ingredient's class. No reviewed reference in the catalog approves the phrase `Vitamin B3` as niacinamide alone, so this change leaves it unresolved. It does not receive the confirmed ID `niacinamide`, and that ID is not stored as its suggestion or as a candidate.

## Belle: catalog import

Today, demo products store ordered ingredient strings and `ingredient_list_status` in `Resources/DemoData/products.json`. Firestore import is not implemented in this PR.

Recommended sequence:

1. Load the alias catalog with `IngredientAliasCatalog.load` or `loadBundled` and create an `IngredientNormalizer`. Do not decode a product inside the catalog loader, and do not load the catalog from `NormalizedIngredient.init(from:)`.
2. Keep the caller's product ID, the original ingredient strings in label order, and the list status the caller already knows.
3. Call `normalizeStoredProduct(id:ingredientTexts:listStatus:)` or, for a current `DemoProduct`, `normalizeCatalogProduct(_:)`.
4. Persist the encoded `NormalizedProductIngredients`, including `catalogVersion`. Do not persist `IngredientAnalysisInput`. Do not replace a row's original text with the canonical name. Do not write `ingredientID` onto an unresolved row.

`normalizeCatalogProduct(_:)` is the current read adapter from string storage to that record. It does not write Firestore.

## Mia: analysis

The analysis engine is not implemented in this PR. Recommended sequence:

1. Decode `NormalizedProductIngredients`. That step validates ID syntax and row shape only.
2. Create an `IngredientNormalizer` from the active catalog.
3. When `catalogVersion` is missing or different, refresh with `normalizeStoredProduct` using the stored product ID, `originalText` values, and list status before treating the mapping as current. Do not reuse an unknown stored ID as a new identity.
4. Read `analysisInput(using:)`. Match rules only against `confirmedIDs`. Ignore `suggestedID` and `candidateIDs`. When `uncertaintyPreserved` is true, do not treat the product as fully checked or safe. That includes a missing or stale catalog version, a partial list whose present rows all confirmed, an unavailable list, an empty complete list, a contradictory list status, and a complete list that still contains an unresolved or unknown ID.
5. Keep the full `ingredients` array when a result needs to explain an unresolved line. Those rows are present and unresolved. They are not the same as ingredients that were absent from the label.

Confirmed IDs are the stable identity shared by alias spellings. `Nicotinamide` and `Niacinamide` both produce `niacinamide`, so a later rule can evaluate them as the same ingredient. The original spellings remain on the rows. A confirmed ID means the stored claim names one catalog ingredient. It does not mean the ingredient or the product is safe.

| Issue #19 criterion | Covered here | Still outside this PR |
|---|---|---|
| A known alias maps to the canonical ID | Normalizer tests, including Nicotinamide to `niacinamide`, and the product example | None for the mapping itself |
| An unmatched ingredient is not treated as safe | Unmatched, uncertain, and ambiguous rows have no confirmed ID. Decoding refuses to add one. Unknown stored IDs are omitted from analysis input, and `uncertaintyPreserved` stays true | The analysis screen does not yet consume this record |
| Original text and the normalized result stay traceable | `originalText` is kept in order on each row. Profile summary already shows entered text beside a confirmed name | Catalog product-detail UI still shows the demo strings only |
| Different aliases of the same ingredient evaluate consistently | Confirmed rows share one ID. `analysisInput(using:).confirmedIDs` is the list a rule can compare after catalog membership is checked | Rule evaluation itself |
